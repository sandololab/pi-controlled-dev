# Preparazione di un nuovo progetto

L'ingresso corrente `/controlled-dev` e il suo alias `project new` operano nella cartella corrente attraverso `CurrentProject` e Project Planning nativo. Il wizard separato per scegliere una destinazione è stato ritirato. Questo documento descrive il motore bootstrap conservato e i suoi artifact storici; il [manuale corrente](USER-MANUAL.md) descrive il percorso utente.

Gli artifact Proposal, Intent e Result a livello di progetto riusano gli artifact canonici immutabili di DurableStore e il suo indice CAS atomico. Non introducono stati, transizioni, ledger di task, un secondo WAL, planner, ciclo di memoria o esecutore Git. Il workflow congelato resta 11/43.

Lo Scout pre-task in sola lettura dispone di un formato aggiuntivo di proposta analitica e di una skill del package. Legge le guide installate prima che esista una destinazione; il percorso Project Planning esistente legge poi il progetto inizializzato e la memoria nativa. Le scelte tecniche sono valori ProjectMemoryProposal nativi con scope repository, mai lezioni, affermazioni sui sorgenti o decisioni implicitamente vincolanti. Lo schema del modello deriva varianti di contenuto chiuse per tipo dai frammenti wire della memoria esistente, coerenti con i validator nativi; una convenzione non può contenere campi di ADR o vincoli. Campi inattesi vengono rifiutati, mai rimossi silenziosamente. Le correzioni in linguaggio naturale creano un'altra bozza esatta. Il vecchio wizard bootstrap gestiva pannelli di chiarimento e approvazione esplicita della creazione. Project Planning corrente conserva domande aperte e risposte umane fra annullamento e riapertura, separa correzione e approvazione del piano e non tratta mai un chiarimento come permesso di avviare Developer. Dettagli reversibili dell'applicazione vengono proposti per revisione, senza bloccare una baseline Git vuota.

La conferma bootstrap lega anchor/leaf della destinazione, identità attesa della directory, obiettivo, preferenze, branch iniziale, strategia della radice vuota e tutte le scelte tecniche iniziali. Request/receipt native locali al processo vengono consumate sotto il workspace lease esistente; JSON copiato non può avviare effetti. Intent ed evidenza di approvazione entrano nell'indice prima di mkdir o inizializzazione Git. Annullare non modifica destinazione o store di progetto.

L'inizializzazione Git host è un metodo CandidateGit limitato che usa l'esecutore privato con allowlist esistente, ambiente sanificato, impostazioni non interattive, identità configurata e policy per hook/firma. Un template vuoto impedisce di copiare hook globali. Una prenotazione esclusiva della directory Git impedisce a due profili di reinizializzare la stessa destinazione. Non importa file, scrive file applicativi, installa dipendenze o configura remoti. L'indice vuoto supporta la normale promozione del primo task senza un workflow di merge speciale.

Gli input supportati sono una foglia finale assente con padre canonico esistente, oppure una directory completamente vuota. Repository esistenti con commit vengono reindirizzati; repository preesistenti unborn non sono supportati esplicitamente. Git annidato, symlink, traversal e posizioni del control plane vengono rifiutati. Identità e contenuti della directory vengono ricontrollati dopo l'approvazione e prima di ogni effetto.

Un'identità di progetto portabile è legata al messaggio del commit root iniziale vuoto e a un marcatore tecnico limitato nei metadati Git. I progetti legacy senza marcatore conservano l'identità derivata dal percorso. Memoria, pianificazione, task storage, promozione e checkpoint condividono projectIdentity; i lock workspace restano legati al percorso canonico corrente. Spostare una directory inizializzata completa conserva i record nativi nel medesimo profilo esterno. Questo motore non offre migrazione dei percorsi dei task attivi.

Il recupero legge intent e receipt esatti indicizzati, riacquisisce solo un lease host esatto e verificabilmente morto usando il generation-claim guard esistente di LockManager e riconcilia prove degli effetti limitate. Sono supportati solo intent, directory vuota creata, Git unborn inizializzato e commit root esatto già esistente. L'oggetto commit viene registrato prima dell'aggiornamento della branch; le superfici Git note vengono controllate separatamente. Lacune nelle prove, file extra, metadati/branch/commit inattesi o proprietà del processo incerta restano bloccati. Non tenta rollback, rimozione di directory o reset.

L'indice del risultato conserva riferimenti nativi Project Goal/Project Memory/Project Plan in un artifact di setup, senza copiarne il contenuto semantico o attribuire nuova autorità. I record iniziali restano PROPOSED fino alle conferme native individuali. Project Plan DRAFT, revisione, correzione e approvazione usano ProjectPlanningRepository e PreTaskScout.plan. Il pannello mostra la cartella ufficiale corrente; uscendo conserva la bozza salvata e notifica cartella e stato della bozza con testo dell'host. La directory locale è contesto visivo, non viene salvata negli artifact portabili del piano. Né bootstrap né una bozza non approvata avviano Developer. Un PlannedTask scelto in seguito usa il normale wizard TaskSpec e ControlledTask.

Project.md è una proiezione leggibile dello stato iniziale, obiettivo, memoria accettata e piano corrente, con wikilink relativi. Modificare Markdown non può inizializzare Git o approvare nulla. I test usano Git reale e worker separati per concorrenza/crash, con double UI/provider dichiarati. La verifica end-to-end attraversa due task pianificati nativi, candidate isolate del Developer, Reviewer indipendente, validazione, promozione approvata dall'utente e Integration Checkpoints esistenti. Una prova TUI umana reale e una prova con modello reale sono evidenze distinte.
