# Verifiche di integrazione

Documenti opzionali a livello di progetto; non aggiungono stati, transizioni o gate ai task. Il ciclo della definizione è una proiezione di artifact di bozza immutabili e prove di approvazione nativa trusted. Gli esiti PASS/FAIL/BLOCKED dei run sono fatti documentali. I run conclusi restano immutabili; le fasi parziali conservano identità e prove esatte.

Il namespace di progetto `integration` nel DurableStore esistente possiede questi artifact. Il breve mutation guard del workspace serializza il CAS dell'indice senza acquisire autorità di scrittura sul progetto originale; un task lease esistente legato a revisione della definizione e commit esatto serializza run equivalenti. Il recupero richiede l'esatta incarnazione host terminata, usa il generation-claim guard esistente e registra BLOCKED senza rieseguire comandi. Un run terminale può rilasciare il proprio lease residuo esatto e morto senza cambiarne l'esito persistito. Un intent di comando o dispatch Reviewer non dimostrato resta inammissibile per un nuovo dispatch equivalente.

La copertura richiede una storia del task COMPLETED verificata e un binding Candidate Promotion congelato. Un task modificato richiede anche un PromotionResult autenticato il cui commit di integrazione sia antenato della baseline esatta. I task no-op richiedono una candidata congelata invariata e un completamento dimostrati. Riferimenti espliciti al piano devono corrispondere a revisione corrente approvata e collegamenti alle esecuzioni. Gli scenari esistenti devono risolversi in artifact immutabili dei task selezionati e hash di comando esatti compatibili.

L'host riusa il compilatore chiuso delle ricette, l'esecutore/raccoglitore di prove dei processi condiviso, Scenario Management e Runtime Observability. Una ricetta REVIEW non può disabilitare il Reviewer esistente: non ha un comando di processo e deve conservare la propria esecuzione reale di review. Le prove del checkpoint hanno un envelope baseline/run di progetto; non sono accettate nel workflow di un task. File tracciati, HEAD e indice del worktree devono restare legati al commit. Output build/test non tracciati sono ammessi soltanto nella copia isolata; copie sporche vengono conservate quando la normale pulizia Git le rifiuta.

Lo stesso ingresso di integrazione di controlled.reviewer mantiene contesto nuovo, strumenti in sola lettura, enforcement di transcript/extension e prova terminale esatta. Il packet limitato fornisce risultati dei task, promozioni autenticate, definizione, evidenze di validazione/scenari/runtime e riferimenti esatti allo store per ulteriori letture. Digest e tupla terminale vengono persistiti e controllati al reload. Le prove dei comandi legano cwd alla copia isolata univoca del run, inclusi scenari che mantengono un task ID originale; prove di vecchi run non possono essere riassociate a nuovi run. Project Memory usa selezione limitata esistente e ricevute di dispatch reali; pianificazione/selezione deterministica host è etichettata HOST_CONSUMED, mai come riconoscimento del provider.

Un canary sul progetto originale rifiuta modifiche non spiegate. L'unica alternativa a file originali byte-identici è una destinazione pulita avanzata attraverso una catena esatta di PromotionResults trusted, approvati e persistiti; configurazione Git sensibile e hook restano invariati. I byte fisici devono corrispondere al digest di integrazione approvato anche se flag dell'indice Git nascondono modifiche del worktree. JSON o callback con la stessa forma non possono evitare questo controllo. Commit/ref arbitrari o modifiche sporche dell'originale vengono rifiutati. La destinazione non resta bloccata per tutta la verifica.

Lo stato corrente di integrazione deriva dai run e dall'identità della destinazione corrente: NOT_CHECKED, VERIFIED, FAILED, STALE. PASS resta collegato al vecchio commit quando la destinazione avanza. Questa vista non autorizza né blocca future promozioni. Completamento, integrazione e verifica della baseline restano distinti.

Non introduce scheduler, secondo orchestratore, secondo reviewer, shell fornita dai modelli, strumentazione dei sorgenti, riparazione/rollback automatici, Git remoto o autorità Systemist. Note Markdown e Obsidian sono proiezioni rigenerabili.
