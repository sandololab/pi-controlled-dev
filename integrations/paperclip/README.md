# Paperclip human transport (pilot)

This optional host adapter connects a **live native Pi session** to Paperclip issue interactions. The native worker is checked with Pi 1.5.2 and pi-subagents 0.88.1. Its HTTP contract follows the interaction, issue-document and execution-policy APIs documented for Paperclip v2026.1106.0; deployments must verify their installed server contract. It is a pilot adapter, not a claim that a real human or real-model acceptance campaign has passed.

## Trust boundary

The native extension still owns task state, freshness, validation, independent review, locks and one-use confirmations. An external host registers a process-local, session-bound capability through `createExternalHumanContext` (or the trusted host event in the loaded extension module graph). Merely supplying `mode: external-human`, a JSON receipt, a model tool or an RPC boolean does not register a channel. Terminal-only input handling and the existing human-probe diagnostics remain terminal-only.

The Paperclip daemon is outside the model's filesystem sandbox. The worker is inside it. The administrator must supply the confined `workerArgv`, pin package/SDK paths and the Paperclip API origin, keep the private job directory inaccessible to model tools, and acquire the installation's global production lock before launching the daemon. No installer or permission changes are performed by these files. This is trusted host code; it cannot protect against an administrator, compromised host runtime or arbitrary extension code with access to its process memory.

The worker and daemon exchange signed messages using a random, per-process key passed over private stdin. The key is never put in the environment, project, session transcript, job manifest or controller output. Worker stdout without a valid signature cannot publish a human question. Paperclip credentials are supplied by each current assigned agent run over a private Unix socket, validated against the job and `/agents/me`, and are never forwarded to the worker or persisted. API redirects are rejected. Do not recover credentials from process inspection, old logs, cookies or files.

Every question preserves the complete native presentation in an issue document. Confirmations target that exact document revision. Questions carry its revision in their presentation and revalidate it before accepting a reply; long presentations remain in the linked document. Text answers accept the canonical Paperclip representation (`optionIds: []` plus `otherText`) and the explicit legacy text option; an empty selection without text, a contradictory choice or an agent resolution cannot authorize a response. Only a resolved `human_only` interaction attributed to a user can return a response to Pi. A different assignee/company, changed content, stale document, agent resolution, cancellation, expiration or uncertain result cannot grant approval. Native guards run again when consuming a confirmation.

## Host configuration

Create a private directory (0700) with `job.json` (0600), then run:

```sh
node integrations/paperclip/daemon.mjs /private/jobs/JOB/job.json
node integrations/paperclip/controller.mjs /private/jobs/JOB status
node integrations/paperclip/controller.mjs /private/jobs/JOB tick
node integrations/paperclip/controller.mjs /private/jobs/JOB command controlled-dev 'status --technical' status-001
node integrations/paperclip/controller.mjs /private/jobs/JOB stop
```

Mutating controller actions require the current `PAPERCLIP_API_URL`, `PAPERCLIP_API_KEY`, `PAPERCLIP_COMPANY_ID`, `PAPERCLIP_TASK_ID`, `PAPERCLIP_AGENT_ID`, and `PAPERCLIP_RUN_ID`. The assigned issue must have a real project and be in progress or in review. The controller sends credentials transiently; do not put them in `job.json` or shell arguments.

The manifest contains `version: 1`, a unique `id`, `profile` (`sviluppo` or `redazione`), `project`, `apiUrl` (without `/api`), `companyId`, `issueId`, `agentId`, `workerArgv` (sandbox command and arguments), and `workerConfig`: absolute `sdkEntry`, `sessionDirectory` **outside the project Git tree**, `profile`, and exact `model: {provider, id}`. Optional `workerConfig.packages` is an administrator-supplied, in-memory resource override for isolated staging tests. Optional `initialCommand: {name,args,commandId}` starts only after an authenticated assigned run connects. Use a new job ID for a genuinely new session.

Development supports the native `controlled-dev` command. The editorial companion must preserve full non-terminal proposal/question presentations; the adapter supports its team `editorial create`, `revise` and `workspace-*` commands, plus `photobook`. Legacy terminal-only editorial run/decision/voice flows are deliberately rejected. No terminal mode or automatic affirmative UI is simulated.

## Continuation, stop and recovery

The controller `tick` performs bounded work (at most 30 seconds), publishes one pending interaction and returns. Human waiting uses Paperclip's `wake_assignee`; on wake the assigned agent calls `tick` again with its new run context. While native work runs without a human question, the adapter uses Paperclip's **timer-based issue monitor**, not another scheduler: one-minute checks, a 30-minute active-work budget per command (paused while waiting for a human) and at most 30 polling attempts. The agent must preserve and call the same job ID. A null execution policy uses the server’s normal defaults (`mode: normal`, comments required, no added review stages); explicit review, authorization and other policy fields are preserved. A pending human interaction clears the worker monitor.

Assign and retain a unique command ID before the first submission if a Paperclip wake or retry may repeat it. Reuse that ID with the same command and arguments in the same job. The controller generates a new ID on each invocation when omitted. After checking the current assignment, the daemon returns `commandReplay` with the original worker result, or `result: null` while no worker outcome has been recorded. Use `tick` to continue the same live job. Reusing the ID with different arguments or a different command fails with `BRIDGE_COMMAND_ID_CONFLICT`. If the daemon has exited or the outcome remains uncertain, inspect the saved job evidence and native workflow state before deciding whether to issue a new command. A job directory with existing state cannot launch another daemon.

`idle` or `command-finished` means only that a host command returned. It does **not** certify project completion, validation, independent review or integration. Inspect the native state/evidence; the supplied native status explicitly does not infer integration. Editorial completion must be read from its native workspace.

`stop` validates the current Paperclip assignment, immediately asks the worker to abort native work, and starts a 30-second termination watchdog. The worker awaits the native `session_shutdown` hooks and disposes the session before acknowledging a clean stop. A denied shutdown or an exit without that acknowledgement is recorded as interrupted. Paperclip interaction withdrawal and monitor clearing run concurrently with native shutdown. Remote cleanup failures remain in `withdrawError` or `monitorClearError` and in the job events. An authorized current run can clear obsolete cards or monitors. The daemon preserves the local shutdown and remote cleanup outcomes before exiting. The administrator's lock must be inherited by the daemon and released on exit. The daemon must run in a persistent administrator-managed process context, outside ephemeral tool namespaces: `start_new_session` alone cannot survive their destruction. A deployment wrapper should prepare the job for an authorized operator, who verifies its exact sandbox command, pinned package/model/configuration and assigned task before starting that specific job as a bounded service. Never expose a generic host command launcher to the model. The service keeps the existing worker confinement and receives no Paperclip API credentials at boot. After a verified interruption, archive the old job/state/events unchanged and create a fresh job/session; do not restart the frozen state or replay decisions. The session has an eight-hour maximum lifetime. If interrupted, preserve evidence, withdraw obsolete cards through an authorized current run, and inspect native recovery. Never replay a previous response into a new worker/session or silently rerun a mutating command. A saved JSON response grants no permission.

## Verification and remaining acceptance

`test/external-human-paperclip.test.mjs` exercises native one-use receipts, session/revision binding, denied forged/agent responses, document/question integrity and transport signatures. `test/paperclip-daemon.test.mjs` exercises the private daemon with a **synthetic** HTTP server and child fixture. These are not human acceptance evidence. `test/paperclip-worker.test.mjs` checks ordered native shutdown and refusal of blocked shutdown with a declared SDK double. The opt-in `test:pi-integration` suite also launches the real worker with the installed Pi SDK and a temporary profile without real credentials; its status/stop probe makes no model request. Set `PI_TEST_HOST_ROOT` and `PI_TEST_SUBAGENTS_ROOT` to the selected installed packages. Run the existing affected native confirmation/UX suites, typecheck and integration-checkpoint suite with enough time for its real Git/fsync/crash fixtures (several minutes on slower disks). Do not replace their assertions or treat a timeout as a pass.

Before the first real commission, verify a real Paperclip card, an actual owner's response, wake-up into the same live Pi session, cancellation/interruption and native completion/review evidence. Keep deployment local configuration, credentials, client data, raw sessions and machine-specific logs out of this repository.

### Photographic workflows

The native `/photobook` command delegates to a Pi model conversation. The worker therefore uses the actual SDK `prompt` and `waitForIdle` boundaries, records native tool-call names and IDs, and returns the exact assistant presentation through a human-only conversational question. A reply continues the same Pi session. This conversational input is not a domain approval receipt, integration authority or author release. Existing photobook domain constraints remain in force. The administrator pins the same model; no alternate provider is chosen. The bounded defaults are four model turns and 120 tool calls. The final budgeted turn is recorded as a notice without collecting a reply that cannot be applied. A new mandate is needed to continue beyond the budget. Native outputs still require inspection and independent quality review.

The daemon enforces the active-work time budget even when no controller polls. Human waiting pauses that clock; the separate eight-hour session lifetime still applies. A killed worker leaves interrupted evidence, not a completed commission.

The historical HTTP composer asset patch is outside this transport.
