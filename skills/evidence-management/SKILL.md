# Evidence management

This guide is not authority and cannot declare a task complete, an approval valid or a system requirement satisfied.

## Structured evidence

- Link each criterion explicitly to evidence references. Do not rely on ordering, position or textual similarity.
- Distinguish present evidence, missing evidence and technical outcomes `PASSED`, `FAILED` or `BLOCKED`.
- Verify scenario, validation, command and candidate identities before using evidence.
- Preserve runs, validations, runtime events, before/after comparisons, patches, reviews and residual risks as attributed references.

## Readable report

- Write in natural English and separate observed facts, technical interpretation and limitations.
- Use stable frontmatter and wikilinks for internal notes.
- Keep technical details in a dedicated section.
- Remember that Markdown is a projection: manual edits do not change the store.
- Preserve user annotations in separate notes that regeneration does not overwrite.

State when evidence is insufficient. Do not promote uncertainty to PASS.
